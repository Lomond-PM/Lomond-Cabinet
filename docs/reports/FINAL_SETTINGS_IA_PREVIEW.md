## B. Implemented Information Architecture

The live composition in `renderSettingsContent()` now produces exactly:

```
Global Settings  (single scroll root, .settings-renderer.settings-root-page)
├─ General         [Disclosure: expanded]  data-settings-disclosure-key = settings.general
│  ├─ Language            -> #settingsLanguageMount        (renderSettingsLanguage)
│  ├─ Interface           -> #settingsInterfaceMount       (renderSettingsMotion; uiScale row)
│  └─ Motion              -> #settingsMotionMount          (renderSettingsMotion; motionSpeed row)
├─ Appearance      [Disclosure: expanded]  data-settings-disclosure-key = settings.appearance
│  ├─ Core Appearance     -> #settingsCoreAppearanceMount      (renderSettingsTheme coreMount = interfaceAppearance group: Accent / Base Canvas)
│  ├─ Semantic Appearance -> #settingsAppearanceParametersMount (setupAppearanceSubpage, AppearanceParameterRegistry EXPOSE_NOW)
│  ├─ Typography          -> #settingsAppearanceParametersMount
│  ├─ Tool Icon           -> #settingsProceduralAppearanceMount (renderSettingsTheme appearanceMount = non-core theme groups)
│  ├─ Background          -> #backgroundSettingsCard            (renderSettingsBackgroundEngine; nested Appearance disclosure)
│  └─ Palette Library     -> #settingsPaletteLibraryMount       (Palette Library -> Workspace)
├─ Advanced        [Disclosure: collapsed] data-settings-disclosure-key = settings.advanced
│  └─ Developer Access    -> #settingsDeveloperModeMount     (Developer Mode toggle; Developer Mode -> Home lab visibility)
└─ Developer       [Disclosure: collapsed, gated] data-settings-disclosure-key = settings.developer, class settings-category--developer settings-developer-only
```

Category ordering (top-level) is now **General, Appearance, Advanced, Developer**. `General` and `Appearance` default expanded (`expanded === true`); `Advanced` and `Developer` default collapsed (`expanded === false`).

## G. Design Tuning Consolidation

The Developer category previously exposed two sibling entries at the top level:
- `settingsDeveloperDesignTuningMount` (header "Design Tuning" + motion/domain/appearance groups).
- `settingsDeveloperCalibrationMount` (header "Home Calibration" + `homeIconRadius` / `homeDragShadowIntensity` rows).

**Goal** (user-approved): one user-visible "Design Tuning" product-level entry, with the calibration row set as an internal multi-group — no two overlapping Design Tuning / Calibration entries.

**Implementation** — new `createSettingsDesignTuningSection()`:
- Builds `#settingsDeveloperDesignTuningSection` (`class="settings-design-tuning-section"`, plain grouping container).
- Prepends a single section header: overline `settings.navigation.developer` + title `settings.designTuning.title` ("Design Tuning") + description `settings.designTuning.description`.
- Nests `settingsDeveloperDesignTuningMount` + `settingsDeveloperCalibrationMount` as the two internal mounts.
- The redundant internal "Design Tuning" header that `renderSettingsDesignTuningMotion()` previously emitted was **removed** (the section header now lives on the wrapper). The internal groups (Motion, spacing/radius/controls/elevation/text/surface/border domains, Existing Appearance, Reset All, Evidence) are unchanged.
- `settingsDeveloperCalibrationMount`'s internal header was changed from a `createSettingsSectionHeader("section.debug", "settings.developer.homeCalibration", null)` to a `createSettingsGroupLabel("settings.developer.homeCalibration")`, so it reads as an internal group rather than a second entry. The `section.debug` key remains in use by the Advanced Developer-Mode header, so no key is orphaned.
- New CSS rule `.settings-design-tuning-section` (flex column, `gap: var(--space-settings-section-stack)`, `min-width: 0`) provides vertical spacing between the header, the tuning mount, and the calibration mount; it reuses the existing stack token and does not alter any canonical value.

**Why this shape (and not moving calibration into the tuning mount):** The design-tuning mount is re-rendered via `renderSettingsDesignTuningMotion()` on every Settings open (`openSettingsPanel`, `is-open` branch), which clears `mount.innerHTML`. The calibration inputs are **settings-schema fields** restored from persisted state by `loadPersistentState()` (only at startup, not on re-open), so placing them inside the re-rendered mount would reset them to defaults on each Settings open. Keeping `settingsDeveloperCalibrationMount` as a distinct mount (filled once, never wiped) and grouping it under the single Design Tuning section preserves the saved values while delivering the user-visible one-entry IA.

**Authority unchanged:** No DesignTuning state store, resolver, off registry, or override creation path was touched. The calibration rows remain schema-rendered settings fields.

## Z. Developer Mode → Settings → Home Transition Repair (AE REVIEW FAILED)

### Defect (real AE repro)

```
1. Developer Mode = ON
2. Open Global Settings
3. Advanced -> Developer Mode -> OFF
4. Developer content hides as expected
5. Click Back / Return Home
6. Settings exit animation completes (content disappears)
7. [BROKEN] Settings -> Home transition continuation never happens
8. Blank work-surface "transition carrier" persists forever
9. Home enter never runs
```

This is **not** "Home entered but empty". It is: **Settings exit completed, but the Settings → Home transition continuation did not complete.**

### Root cause

- Every home entry — **including the Settings gear** — is created by `renderDynamicToolHome()` with `homeOwnership: "dynamic"` (the catalog marks all home-visible entries `homeOwnership: "dynamic"` in `getHomeEntries`).
- Toggling **Developer Mode OFF** runs `applyRegistryDebugTools(false)`, which calls `renderDynamicToolHome()`. That tears down and rebuilds the whole Home tool grid, **detaching the previously captured Settings gear node.**
- The captured `ActiveSettingsSourceElement` therefore becomes a **detached** node.
- On **Back**, `closeSettingsPanel()` read `source = ActiveSettingsSourceElement` (the detached node), so `getHomeToolIconRect(source)` returned a `(0,0,0,0)` rect → `SurfaceIdentity.snapshot()` returned `null` → `SurfaceIdentity.composite()` returned `null`.
- With a null destination identity, `createSurfaceIdentityOverlay()` returned `null`, and `closeIdentityKeyframes()` / the overlay `.style` access would **throw**, aborting `closeSettingsPanel()` **before** `beginSpatialSurfaceMorph()` ever scheduled the transition gate.
- Result: `finishCloseSettingsTransition()` (the single Home destination commit) never ran → the transition froze on the empty carrier.

Classification: **EXISTING_DEVELOPER_MODE_LIFECYCLE_BUG_EXPOSED** (Home re-render invalidating a captured source identity), manifesting as a **navigation-transaction / DOM-lifecycle defect**. It is **not** a Final Settings IA regression — the General / Appearance / Advanced / Developer composition does not touch Home rendering or the transition.

### Fix

In `client/js/main.js` `closeSettingsPanel()` — the transition **source-ownership** seam:

- Resolve `source` to a **live** element: keep `ActiveSettingsSourceElement` only if it is still in the document; otherwise **re-query** `HomeLayoutManager.getButtonByToolId("settings")` for the current in-DOM gear, and refresh `ActiveSettingsSourceElement`.
- If there is no live source, **fall back to `finishCloseSettingsTransition()`** (the formal Home commit) instead of aborting.
- **Guard the destination identity**: only composite when a valid snapshot exists; if either the source or destination identity is uncomputable, **fall back to `finishCloseSettingsTransition()`** — guaranteeing the transition always reaches exactly one Home destination commit.
- **Guard the close identity overlay** (`if (identityOverlay)`) so a null identity can never null-deref and abort the transition.
- A **valid** close still runs the real Surface Transition gate (`beginSpatialSurfaceMorph("system:view", backdrop ? 3 : 2, …)` → `finishCloseSettingsTransition()`), and the destination geometry is drawn from the live resolved source. No Back-button force-render / `setTimeout` / transition-disable was added.

This is an ownership/lifecycle fix, not a local Back-button patch: it restores the existing "Settings exit → destination commit → Home enter → finalize" continuation and makes it resilient to a stale source across a Home re-render.

### Verify

- `scripts/test-developer-mode-settings-return.js` (new) locks the transition-continuation contract: live-source re-resolution, stale-source fallback, null-identity fallback, overlay guard, real-gate-on-valid-close, single Home commit, no Back-button hack, no `activeToolId` dependence.
- Existing Surface Identity / Settings Peek / Presentation Session / Design Tuning / Palette Workspace tests still pass.
